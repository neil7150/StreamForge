# StreamForge Android audit

Audit date: 12 September 2026. Source: the current working tree in C:/Users/neilr/Desktop/Torrent, checked against the pasted request.

**The scaffold is not yet capable of torrent playback.** Adding a video view alone will not fix it: source selection discards the magnet, no mobile screen adds a torrent, the daemon has compile errors, and there is no Android binding or native startup. There are also independent catalog, login, library, and persistence defects.

This is an audit and implementation plan; application source was not changed. Existing worktree changes were preserved.

Read the [architecture and implementation roadmap](C:/Users/neilr/Desktop/Torrent/docs/streamforge-mobile-architecture.md) alongside this issue register.

## Corrections to the pasted assumptions

- The real API client already reads `EXPO_PUBLIC_API_BASE_URL`, then `VITE_API_BASE_URL`; it does not only read `VITE_API_URL`. The remaining problems are configuration placement, unvalidated values, and the device-local default.
- Stores do have persistence code, but their synchronous default adapter falls back to an in-memory map on mobile. AsyncStorage cannot simply be assigned to that interface.
- Home nests **horizontal** FlatLists in a vertical ScrollView. That is not proof of the same-orientation VirtualizedList warning. Its nonvirtualized outer feed is a scaling concern; SeriesDetail's `episodes.map` is the clearer current virtualization problem.
- `React.FC` is not inherently broken everywhere under React 19. Current navigator screens use compatible typed functions and typecheck. UI components using FC are not a finding.
- Installed RN has removed `absoluteFillObject`; current source uses explicit edges. There is no remaining occurrence to fix.
- Expo's entry point loads its winter runtime, which patches `AbortSignal.timeout`. RN's standalone abort-controller lacks it, but calling that a confirmed failure in this Expo app would be wrong.
- Search's no-results swarm search is user-triggered, not automatic.
- The Go engine/server/bridge are actual implementations with defects, not merely the comments shown in the attachment.

## Priority definitions

P0: prevents building/core playback, reproducible source-level crash path, or serious destructive behavior. P1: incorrect functionality, data integrity, lifecycle or security defect. P2: performance, accessibility, reliability and UX. P3: maintainability and lower-impact correctness.

**Count: 8 P0, 44 P1, 22 P2 and 8 P3 findings (82 total).** Fix P0 first. P1 native issues describe behavior that becomes reachable after the build/binding blockers are removed.

## Highest-value regression cases

1. Failed credentials leave Login visible with the store's error.
2. Library toggles lists repeatedly without invariant failure.
3. Real backend show JSON with genre objects and E5 opens E5 sources.
4. Real movie JSON with magnet_links uses those sources.
5. Cold-start magnet waits for hydration/navigation and is consumed once.
6. Full magnet, content identity and file index survive source selection and resume.
7. Changing source/season/query while an old request resolves cannot overwrite the current session.
8. A ten-second history cadence writes about once per interval, plus explicit terminal flush—not on every time event.
9. Account A → logout → B never exposes/uploads A's private list, including delayed A responses.
10. Stream range requests use independent readers, close on disconnect, serve selected file bytes and remain cancellable during missing pieces.
11. Restart/stop while adding metadata produces no stale URL, leaked reader, panic or new-generation cleanup.
12. Missing engine, port conflict and unsupported media produce explicit recoverable errors instead of fabricated ready state.

The architecture document turns these into build milestones and release acceptance gates.
